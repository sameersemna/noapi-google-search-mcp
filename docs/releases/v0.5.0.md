# v0.5.0 — honest packaging, a real page-text limit, and no proxy in the middle

Released 2026-11-05. 43 tools, zero API keys.

This release is mostly about two kinds of honesty: the package now installs on
every Python version it claims to support, and settings that are documented
actually do something.

## Installs on Python 3.13

`pip install noapi-google-search-mcp` failed on 3.13, because
`rapidocr-onnxruntime` declares `Requires-Python <3.13` upstream
([RapidAI/RapidOCR#579](https://github.com/RapidAI/RapidOCR/issues/579)) — so it
could never be satisfied as a hard dependency. The package advertised 3.13
support anyway, and CI ran the 3.13 job with `continue-on-error`.

OCR is now an optional extra:

```bash
pipx install "noapi-google-search-mcp[ocr]"    # Python 3.10–3.12
pipx install noapi-google-search-mcp           # anywhere, including 3.13
```

Both OCR entry points — `ocr_image` and the scanned-PDF fallback in
`read_document` — return a one-line install hint instead of raising. Everything
else works without the extra, including `read_document` on text PDFs.

The 3.13 CI job is now **blocking**, and `playwright` is floored at `1.48.0`,
the first release that officially added and tested 3.13.

### Two dependencies were declared only by accident

- `av` (PyAV) is imported by `extract_video_clip` and was **never declared**, so
  clip extraction failed on a clean install.
- `onnxruntime` was imported by the neural-net CAPTCHA solver and arrived
  transitively through `rapidocr`. Moving OCR to an extra would have taken it
  away and silently disabled the solver.

Both are now core dependencies.

### A scanned PDF no longer looks like a blank page

The `rapidocr` import sat inside `except Exception: pass`, so "no OCR installed"
and "this page has no text" were indistinguishable — the tool reported "could
not extract text from <file>". The PDF path now checks for the extra explicitly,
skips the `pdftoppm`/OCR work entirely when it is absent, and names the extra in
the hint.

## `visit_page` returns as much text as you ask for

The limit was a hardcoded 8000-character module constant, so the `env` block
people reasonably reached for did nothing. Worse,
`NOAPI_MCP_MAX_TEXT_CHARS` was documented as a "generic text cap" while no code
path read it.

Set it per process:

```json
{ "env": { "NOAPI_MCP_MAX_PAGE_CHARS": "20000" } }
```

or per call, which is what a model should do when it hits the truncation marker:

```json
{ "url": "https://docs.example.com/guide", "max_characters": 40000 }
```

`max_characters` / `NOAPI_MCP_MAX_CHARACTERS` are accepted as environment names
too, because that is the spelling people try first. Values are clamped to
**200000** — this text lands in a context window, and a tool that can silently
return a megabyte turns one careless page visit into a blown context. A value
that is not a positive integer is ignored rather than fatal, so a typo cannot
stop the server from starting. The cap is part of the cache key, so asking for
more text is never answered from a shorter cached entry.

## No proxy in the middle

`python -m google_search_mcp --transport streamable-http` binds the port itself
and serves `/mcp` (streamable HTTP) plus the deprecated `/sse` + `/messages/`
transport. The Node proxy was an extra process, an unpinned `npx -y` download on
every restart, and a deprecated transport on the wire — and its `--transport`
flag never existed (`--server` is the real one), so the unit file's stated intent
had always been silently ignored. See
[ADR 0007](../adr/0007-native-http-transport.md).

`NOAPI_MCP_HTTP_STATELESS` serves `/mcp` with no session registry at all, which
is the right model for a client that POSTs once per tool call and never resumes.

## `--manual-browser`

Opens a visible Chromium window that shares the server's **session** (cookies),
for the cases only a human can handle: logging in, clearing a consent dialog, or
finding a feed URL.

```bash
noapi-google-search-mcp --manual-browser
noapi-google-search-mcp --manual-browser "https://news.ycombinator.com"
```

It does **not** reuse the service's profile: that profile is held by the service
for its lifetime, is ~1.3 GB, and its `Cookies` file is SQLite, so a second
writer risks corruption. The window uses its own profile and re-saves cookies to
`~/.google_mcp_cookies.json` every 5 s and on close — the file the server reads
on its next browser tool call.

## `google_search_tabs_urls` (43rd tool)

Reports the vertical tabs Google exposes on a SERP (`AI Mode`, `Images`, `News`,
`Videos`, `Forums`, `Web`, `Books`, …) and, with `include_sections=True`, the
result-type sections mixed into the page.

## Everything else in this cycle

- **`/health` reported the wrong transport.** The field was hardcoded to
  `"transport": "stdio"`, so every HTTP deployment advertised stdio. The CLI now
  records what it actually serves.
- **Selector rot across the Google verticals**: `google_hotels` now queries
  `google.com/travel/search` and parses travel cards (it used to return the
  Images/News/Forums tab links, because their `href` contained the query);
  `google_books`, `google_news`, `google_finance`, `google_maps_directions`,
  `google_lens` and `google_shopping` all had dead selectors and now anchor on
  structures that exist, with the raw-text fallback labelled so rot can never
  look like data.
- **Two invalid inline JavaScript blocks in `browser.py`** meant Google blocks
  were never classified (`reason=unknown` in the log) and the manual-intervention
  poll never noticed a resolved block. A `node --check` guard now compiles every
  inline script.
- **`yt-dlp` progress output is suppressed unconditionally** — it writes to
  stdout, which *is* the JSON-RPC channel on the stdio transport.
- Shared Chromium pool (8.6×–14.8× faster per call), read-through cache with
  singleflight, idempotency store, token-bucket rate limiter, circuit breaker,
  transient-only retries, SSRF and filesystem guards, typed errors, output caps,
  and 653 offline tests with an 80% core-coverage gate.
