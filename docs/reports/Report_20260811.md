# Fix Report — 2026-08-11

## Problem

The MCP Google service (`mcp-google.service`) was failing to start with:

```
ERROR: [Errno 98] error while attempting to bind on address ('0.0.0.0', 11499): address already in use
```

The health server (a uvicorn/Starlette HTTP endpoint on port 11499) crashed on restart because the previous process's TCP socket was still in `TIME_WAIT`. The systemd service has `Restart=on-failure`, so it kept retrying — but the port never freed fast enough.

---

## Root Causes

1. **No `SO_REUSEADDR` on the health server socket** — uvicorn's `Config` doesn't expose socket options, so the kernel refused to rebind to a port still in `TIME_WAIT`.

2. **No pre-start port cleanup in systemd** — the service had no `ExecStartPre` to kill lingering processes on the health port (11499) or proxy port (11403) before starting.

3. **Bind failure was fatal** — if the health server couldn't bind, the entire MCP server process crashed. The health endpoint is a monitoring convenience; the MCP tools (search, news, etc.) should work without it.

4. **`__main__.py` was empty** — contained only a docstring with no actual entry point code. `python -m google_search_mcp` did nothing.

5. **`restart_server.sh` was empty** — contained only `#!/bin/bash` with no commands.

---

## Changes Made

### 1. `src/google_search_mcp/health_server.py` — SO_REUSEADDR + Non-Fatal Bind

**What changed:**
- `HealthServer.start()` now creates a TCP socket manually with `SO_REUSEADDR` (and `SO_REUSEPORT` on Linux 3.9+) before passing it to uvicorn via `server.serve(sockets=[sock])`.
- Added a retry loop: 3 attempts with 1-second delay between each.
- If all bind attempts fail, the health server logs a warning and **continues without the health HTTP endpoint** — the MCP tools remain fully functional.
- Added `is_running` property so callers can check if the health server actually started.
- `stop()` now properly closes the pre-bound socket.
- Removed the old `_discover_actual_port()` method (no longer needed — we get the port directly from our socket).

**Key design decisions:**
- Health server is **non-critical**. MCP tools work without it.
- Manual socket creation is cleaner than monkey-patching uvicorn internals.
- `SO_REUSEPORT` is tried but not required (graceful fallback on older kernels).

### 2. `mcp-google.service` — Systemd Hardening

**What changed:**
- Added `ExecStartPre` to kill lingering processes on port 11499 (health) and 11403 (proxy) before starting.
- Added `ExecStartPre` to clean up the stale `service.pid` file.
- Added `KillMode=mixed` — sends SIGTERM to the main process, SIGKILL to children.
- Added `KillSignal=SIGTERM` and `TimeoutStopSec=15` — ensures the old process is fully terminated before restart.

### 3. `src/google_search_mcp/__main__.py` — Entry Point

**What changed:**
- Added a proper `main()` function and `if __name__ == "__main__":` block.
- Calls `mcp.run(transport="stdio")` to start the FastMCP server.
- Now `python -m google_search_mcp` actually works.

### 4. `restart_server.sh` — Populated

**What changed:**
- Added full restart logic: stop service → free ports → clean PID → reload systemd → start service → show status and logs.
- Made executable (`chmod +x`).

## Further Considerations

1. **Check for port conflicts**: `sudo ss -tlnp \| grep 11499` — verify no other service uses this port.
2. **mcp-duckduckgo.service**: Ensure it doesn't also try to bind to port 11499.
3. **IPv6 dual-stack**: Consider binding to `::` (dual-stack) instead of `0.0.0.0` for better compatibility.
4. **Google anti-bot detection**: Not addressed in this fix — separate concern tracked in repo memory.
